# Отчёт о качестве данных: Seoul Bike Sharing Demand

## 1. Контекст

Вопрос из [Project Brief](project_brief.md): как различается средний почасовой спрос на прокат велосипедов по часам
суток в разные сезоны и в рабочие, выходные и праздничные дни?

Смысл строки: один час одной календарной даты - суммарное число аренд за этот час во всей системе проката с погодными
и календарными признаками.

Бизнес-ключ: пара `Date` × `Hour`. Его уникальность подтверждена правилом `date_hour_unique`.

Входной файл:

```text
s3://raw/seoul_bike_sharing/ingested_on=2026-10-24/SeoulBikeData.csv
```

Логическая дата загрузки - `2026-10-24`. Аналитический период - весь годовой ряд по дате наблюдения: с 2017-12-01
включительно до 2018-12-01 не включительно. Справочники не используются.

## 2. Профиль

В исходном CSV-файле 8 760 строк данных и 14 полей. Заголовок записан в Latin-1 (символ `°`), а DuckDB 1.1 читает CSV
только в UTF-8, поэтому имена столбцов декодируются из первой строки того же S3-объекта, а данные читаются со второй
строки как строки (`all_varchar`). Для задачи выбраны ключ `Date` × `Hour` и пять полей; для каждого проверены все
8 760 строк:

| Поле                | Тип по автоопределению DuckDB | Тип в staging                     | Примеры значений           | Пропуски / доля |
|---------------------|-------------------------------|-----------------------------------|----------------------------|-----------------|
| `Date`              | `DATE`                        | `DATE` (`rental_date`)            | `01/01/2018`, `01/02/2018` | 0 / 0 %         |
| `Hour`              | `BIGINT`                      | `INTEGER` (`rental_hour`)         | `0`, `1`                   | 0 / 0 %         |
| `Rented Bike Count` | `BIGINT`                      | `INTEGER` (`rented_bike_count`)   | `0`, `10`                  | 0 / 0 %         |
| `Functioning Day`   | `BOOLEAN`                     | `BOOLEAN` (`is_functioning_hour`) | `No`, `Yes`                | 0 / 0 %         |
| `Seasons`           | `VARCHAR`                     | `VARCHAR` (`season`)              | `Autumn`, `Spring`         | 0 / 0 %         |
| `Holiday`           | `VARCHAR`                     | `BOOLEAN` (`is_holiday`)          | `Holiday`, `No Holiday`    | 0 / 0 %         |
| `Humidity(%)`       | `BIGINT`                      | `INTEGER` (`humidity_pct`)        | `0`, `10`                  | 0 / 0 %         |

Повторов по бизнес-ключу - 0: считается как число строк минус число различных пар `Date` × `Hour`. Полных повторов
строк тоже 0. Период: от `2017-12-01` до `2018-11-30`, 365 дат, на каждую дату ровно 24 часа.

Распределение часов по сезонам и признаку работы проката:

| Сезон    | Часов | Прокат работал | Прокат не работал | Дат с остановкой |
|----------|------:|---------------:|------------------:|-----------------:|
| `Winter` | 2 160 |          2 160 |                 0 |                0 |
| `Spring` | 2 208 |          2 160 |                48 |                2 |
| `Summer` | 2 208 |          2 208 |                 0 |                0 |
| `Autumn` | 2 184 |          1 937 |               247 |               11 |

Значимые наблюдения:

- Прокат не работал 295 часов на 13 датах, и во всех этих часах аренд нет. 247 таких часов приходятся на осень (11,3 %
  осенних часов), а 2018-10-06 остановлены только часы 0-6. Если считать нерабочие часы обычными, средний спрос осенью
  окажется заниженным, поэтому они не участвуют в метриках спроса, но сохраняются в staging с
  `is_functioning_hour = false`.
- Документация UCI расходится с файлом: дата записана как `dd/mm/yyyy` (в 5 304 строках первое число больше 12, поэтому
  порядок однозначен), признак работы - `Yes`/`No`. Автоопределение DuckDB само превращает дату в `DATE`, а `Yes`/`No` -
  в `BOOLEAN`; в staging эти преобразования заданы явно и не зависят от автоопределения.

Пример помеченных записей из ноутбука. Влажность по точке росы рассчитана приближением Магнуса только как довод в
пользу решения:

| Дата         | Час | Влажность, % | Температура, °C | Точка росы, °C | Влажность по точке росы, % | Решение                                |
|--------------|----:|-------------:|----------------:|---------------:|---------------------------:|----------------------------------------|
| `2018-05-19` |   7 |            0 |            11,4 |            4,5 |                       62,5 | Флаг: нулевая влажность неправдоподобна |
| `2018-05-21` |   2 |            0 |            13,9 |           −2,1 |                       33,1 | Флаг: нулевая влажность неправдоподобна |

## 3. Правила и результаты

Поля, проверяемые строки, условия, критичность, действия и связь с задачей описаны в разделе «Шаг 3»
[ноутбука](../notebooks/profile_quality.ipynb#rules) рядом с SQL-запросами. Единица порога у всех правил - число
нарушивших строк, пороги заданы переменными в ячейках правил.

| Правило                                 | Проверено | Нарушений |   Доля | Порог       | Сравнение    | Действие      |
|-----------------------------------------|----------:|----------:|-------:|-------------|--------------|---------------|
| `required_fields_present`               |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `date_valid_in_period`                  |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `hour_in_range`                         |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `rented_count_non_negative_integer`     |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `categories_valid`                      |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `date_hour_unique`                      |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `non_functioning_hour_has_zero_rentals` |       295 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `quarantine`  |
| `season_matches_month`                  |     8 760 |         0 |   0 %  | `count ≤ 0` | Не превышен. | `report_only` |
| `humidity_in_physical_range`            |     8 760 |        17 | 0,19 % | `count ≤ 0` | Превышен.    | `flag`        |

Правило `non_functioning_hour_has_zero_rentals` проверяет только часы с `Functioning Day = No`, остальные правила - все
строки, где заполнены проверяемые поля; в этом снимке пропусков нет. Нулевой порог означает, что любое нарушение
требует внимания; действие применяется к записи независимо от превышения порога.

Критических нарушений нет, поэтому записей в карантине нет. Порог превышен только у правила влажности: 17 часов на
пяти датах в мае 2018 года (19, 21, 22, 27 и 28 мая, ранние утренние часы) имеют `Humidity(%) = 0`. Точка росы в эти
часы соответствует влажности 33-72 %, то есть ошибочно именно значение влажности. Эти часы нужны для метрик спроса,
поэтому сохранены с флагом; для погодных срезов уточняющих вопросов их можно исключить по флагу. Значение влажности не
исправляется.

## 4. Подготовленные данные

Выходные пути в S3:

```text
s3://staging/seoul_bike_sharing/source_ingested_on=2026-10-24/staging.parquet
s3://staging/seoul_bike_sharing/source_ingested_on=2026-10-24/quarantine.parquet
```

Фактические преобразования в staging (15 полей):

- имена приведены к `snake_case` без пробелов, скобок и символа `°`, единица измерения указана суффиксом: например,
  `Temperature(°C)` → `temperature_c`, `Rented Bike Count` → `rented_bike_count`;
- `Date` разобрана по формату `%d/%m/%Y` в `DATE` (`rental_date`); целые поля приведены к `INTEGER`, дробные - к
  `DOUBLE`;
- `Holiday` → `is_holiday` (`Holiday` - `true`, `No Holiday` - `false`), `Functioning Day` → `is_functioning_hour`
  (`Yes` - `true`, `No` - `false`);
- добавлен признак `quality_humidity_in_physical_range_violated`: `true` - влажность вне диапазона 1-100 %,
  `false` - нарушения нет.

Карантин сохраняет 14 исходных полей в исходном строковом виде и с исходными именами, `quality_rule_ids` - список
нарушенных критических правил через `;`, `quarantine_reason` - пояснения через `; `. Каждая запись попадает в карантин
один раз. В этом запуске файл карантина пустой, но имеет определённую схему из 16 полей.

Баланс строк: **8 760 = 8 760 + 0**. После чтения записанных файлов из S3 нарушений критических правил в staging - 0,
флаг установлен ровно у 17 строк с влажностью вне диапазона. Агрегаций, отбора нерабочих часов и исправлений по догадке
нет; исходный raw-объект не изменился (ETag, размер и время изменения совпали до и после запуска).

## 5. Воспроизводимость и ограничения

Ноутбук [`notebooks/profile_quality.ipynb`](../notebooks/profile_quality.ipynb) выполнен дважды, каждый раз с чистого
ядра Jupyter и сверху вниз. Результаты совпали:

| Результат проверки через S3     | Первое выполнение | Повторное выполнение |
|---------------------------------|------------------:|---------------------:|
| Raw                             |             8 760 |                8 760 |
| Staging                         |             8 760 |                8 760 |
| Карантин                        |                 0 |                    0 |
| Флаги влажности в staging       |                17 |                   17 |
| Критические нарушения в staging |                 0 |                    0 |

При повторном выполнении оба файла были перезаписаны, а их ETag не изменились (`staging.parquet` - 160 343 байт,
`quarantine.parquet` - 448 байт): содержимое результатов побайтно совпало, дубликаты строк не добавились.

Ограничения:

- признак `Holiday` расходится с официальным календарём выходных Республики Корея (Project Brief, раздел 5.1); правило
  `categories_valid` проверяет только допустимость его значений и не сверяет даты с внешним календарём, поэтому тип дня
  строится по определению источника;
- погодные поля, кроме влажности, правилами не проверялись: для уточняющих вопросов о погоде понадобятся отдельные
  проверки диапазонов (например, видимость ограничена сверху значением 2000 в 2 245 часах).
